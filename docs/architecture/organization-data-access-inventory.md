# Organization data-access inventory

This inventory records the customer-data paths reviewed for roadmap task 0002. The authenticated `User.organization` is the tenant boundary; request parameters never select the Organization used for authorization. Paths described as scoped use the Organization resolved from the authenticated principal or a record already loaded through that Organization.

## Customer-facing routes

| Route / operation                                                                                      | Data path                                                                                                        | Organization boundary                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/v1/clients`                                                                                  | `ClientController` → `ClientRepository.findAll(spec, pageable)`                                                  | The query specification always includes the actor's Organization before optional client filters.                                                                                                                                                                                                                   |
| `GET /api/v1/clients/{id}`                                                                             | `ClientController` → `ClientRepository.findByIdAndOrganization`                                                  | Detail lookup is scoped in persistence; foreign and absent IDs share the not-found response.                                                                                                                                                                                                                       |
| `POST /api/v1/clients`, `PATCH /{id}/risk-rating`, `PATCH /{id}/pep-review`                            | `ClientController` → `ClientRepository`                                                                          | Creation assigns the actor's Organization; mutations load by ID and Organization before save and audit.                                                                                                                                                                                                            |
| `GET /api/v1/clients/{clientId}/beneficial-owners`                                                     | `KycController` → `KycService.listOwners` → `BeneficialOwnerRepository.findByClientIdAndClientOrganizationId`    | Owner rows are filtered by `owner.client.organization.id` in the query. A foreign client ID yields no rows.                                                                                                                                                                                                        |
| `POST /api/v1/clients/{clientId}/beneficial-owners`, `POST /api/v1/clients/{clientId}/kyc/recalculate` | `KycController` → `KycService` → `ClientRepository.findByIdAndOrganization`                                      | The client is resolved with the actor's Organization before mutation or recalculation. Owner completeness queries are also Organization-scoped.                                                                                                                                                                    |
| `POST /api/v1/clients/beneficial-owners/{ownerId}/verify`                                              | `KycController` → `KycService.verifyOwner` → `BeneficialOwnerRepository.findByIdAndClientOrganizationId`         | Foreign owners are treated as not found; recalculation uses the same actor and Organization.                                                                                                                                                                                                                       |
| `GET /api/v1/flags`                                                                                    | `FlagController` → `FlagService.listFlags` → `FlagRepository.findAllByOrganizationId`                            | Tenant is derived from the actor; rows with inconsistent client/transaction Organizations are excluded. Optional filters are applied in persistence.                                                                                                                                                               |
| `PATCH /api/v1/flags/{id}/review`, `POST /api/v1/flags/{id}/escalate-to-str`                           | `FlagController` → `FlagService` → `FlagRepository.findByIdAndOrganizationId`                                    | The scoped load occurs before save, audit, or STR creation. Flag ownership may be derived from its client or transaction client; if both exist, both must match.                                                                                                                                                   |
| `GET /api/v1/reports/str[?submitted=]`, `GET /api/v1/reports/str/{id}`                                 | `ReportController` → `SuspiciousActivityReportRepository` scoped list/detail queries                             | Draft, submitted, and unfiltered lists plus detail lookup derive ownership through the linked flag's client or transaction client; inconsistent links are excluded.                                                                                                                                                |
| `PUT /api/v1/reports/str/{id}`, `POST /api/v1/reports/str/{id}/submit`                                 | `ReportController` → `SuspiciousActivityReportRepository.findByIdAndOrganizationId`                              | Scoped lookup precedes report mutation and audit. Foreign and absent reports share not-found behavior.                                                                                                                                                                                                             |
| `GET /api/v1/reports/ctr`, `POST /api/v1/reports/ctr/{id}/submit`                                      | `ReportController` → `CurrencyTransactionReportRepository`                                                       | List and submission lookups scope through `report.client.organization.id`.                                                                                                                                                                                                                                         |
| `GET /api/v1/reports/exports/str/{id}.pdf`                                                             | `ReportController` → `SuspiciousActivityReportRepository.findByIdAndOrganizationId` → `ReportExportService`      | The report is scoped before export; only submitted reports are exported.                                                                                                                                                                                                                                           |
| `GET /api/v1/reports/exports/annual/{year}.xlsx`                                                       | `ReportController` → `ReportExportService` → STR, CTR, and transaction repositories                              | Organization ID is derived from the principal and passed to every export query and aggregate.                                                                                                                                                                                                                      |
| `GET /api/v1/audit-log[?action=]`                                                                      | `AuditLogController` → `AuditLogQueryService` → `AuditLogRepository.findByOrganizationIdAndAction`               | The service derives the Organization from the actor; the persistence query filters through `auditLog.actor.organization.id`. Actorless system audit rows are intentionally omitted because they have no tenant attribution.                                                                                        |
| `POST /api/v1/import-batches`                                                                          | `ImportController` → `ImportService.createUploadBatch` → `ImportBatchRepository`                                 | The batch receives the actor's Organization at creation.                                                                                                                                                                                                                                                           |
| `GET /api/v1/import-batches`, `GET /api/v1/import-batches/{id}`                                        | `ImportController` → `ImportService.listBatches` / `findBatch` → `ImportBatchRepository`                         | The service derives the Organization and the persistence queries exclude batches whose non-null `importedBy` belongs to another Organization; batches without an uploader remain visible to their owner, while foreign or inconsistent detail IDs return not found.                                                |
| `POST /api/v1/import-batches/{id}/confirm-mapping`                                                     | `ImportController` → `ImportService.confirmAndProcessLocked` → `ImportBatchRepository.findByIdAndOrganizationId` | Processing requires the actor's Organization and preserves the existing uploader check. Each imported client is resolved or created within that Organization; its transactions, screening flags, and reports use that client's ownership.                                                                          |
| `GET /api/v1/insights/summary`                                                                         | `InsightsController` → `InsightsService` → client, flag, and transaction repositories                            | All counts and aggregates use the Organization from the actor. Cache key is `summary:{organizationId}`; eviction is currently global (safe for isolation, not optimized).                                                                                                                                          |
| `GET /api/v1/settings/users`                                                                           | `UserManagementController` → `UserRepository.findAllByOrganizationId`                                            | User rows are filtered in persistence by the actor's Organization. The route is restricted to `ADMIN`.                                                                                                                                                                                                             |
| `POST /api/v1/settings/users`                                                                          | `UserManagementController`                                                                                       | Direct account creation is disabled with the same `501` response for every valid request until the Organization-membership invitation flow exists. The endpoint does not query global email existence, hash/store the submitted password, or audit a user creation.                                                |
| `PATCH /api/v1/settings/users/{id}/reset-mfa`                                                          | `UserManagementController` → `UserRepository.findByIdAndOrganizationId`                                          | Foreign and absent users share the not-found response; the route is restricted to `ADMIN`.                                                                                                                                                                                                                         |
| `GET /api/v1/settings/threshold-rules`, `PUT /api/v1/settings/threshold-rules/{id}`                    | `SettingsController` → `ThresholdRuleRepository`                                                                 | Threshold rules have no Organization relation and are shared by monitoring jobs. Reads are shared. Writes are denied to every current role with method-level authorization until a separately authenticated and audited platform authority is implemented; no Organization role is promoted to platform authority. |
| `GET /api/v1/settings/system-config`, `PUT /api/v1/settings/system-config/{key}`                       | `SettingsController` → `SystemConfigRepository`                                                                  | Rows have no Organization relation and hold shared compliance/retention defaults. Reads are global; `updatedBy` is excluded from JSON. Writes are denied to every current role until a separately authenticated and audited platform authority is implemented.                                                     |

## Background and shared-data paths

| Work                            | Data path                                                                                                                        | Scope / rationale                                                                                                                                                                                                                                                                               |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threshold screening             | `ThresholdScreeningService` → `TransactionRepository`, `FlagRepository`, `CurrencyTransactionReportRepository`                   | Per-client sums and duplicate flag/report checks include the client's Organization. Missing client Organization fails before rules are loaded. Threshold rules are shared configuration (see above).                                                                                            |
| Structuring detection           | `StructuringDetectionService` → `TransactionRepository.findByClientAndOrganizationAndDateBetweenAndTypeIn` and scoped flag count | Transaction window and duplicate checks include the current client's Organization; missing Organization fails closed.                                                                                                                                                                           |
| Due-diligence regime validation | `DueDiligenceRegimeValidator` → `TransactionRepository.sumAmountByClientAndOrganizationAndDateBetween` and scoped flag count     | Both monthly and annual sums include client ID and Organization ID; missing Organization is rejected.                                                                                                                                                                                           |
| Daily PEP review job            | `PepScreeningService` → `ClientRepository.findByPepTrueAndPepLastReviewedAtBeforeOrPepTrueAndPepLastReviewedAtIsNull`            | Intentionally scans all Organizations as a scheduled compliance maintenance job. It returns no cross-tenant data to a user; each generated flag is attached to its own client, and duplicate checks include that client's Organization. Clients without an Organization are skipped and logged. |
| Sanctions screening             | `SanctionsScreeningService` → `SanctionsListRepository.findAll`                                                                  | Sanctions entries and versions are shared reference data. Screening receives a client from an Organization-bound import path and writes the resulting flag/freeze to that client. No sanctions-entry data is presented as customer-owned data.                                                  |
| Import file cleanup job         | `ImportService.cleanupExpiredImportFiles` → `ImportBatchRepository.findByImportedAtBefore`                                       | Intentionally scans expired batches across Organizations for storage maintenance only. It does not return batch data; each path is normalized and constrained to the configured storage directory before deletion.                                                                              |
| Email uniqueness                | User identity database constraint; internal bootstrap uses `UserRepository.existsByEmail`                                        | Uniqueness remains global in persistence, but customer-facing APIs do not expose an existence check. The legacy direct creation endpoint is disabled until account/membership invitations can be implemented without cross-Organization enumeration.                                            |

## Verification status

- Focused unit tests assert the Organization ID passed from the authenticated principal for flags, insights, KYC, reporting, imports, audit logs, user listing, and monitoring duplicate checks. Import and audit reads now pass through services. Missing Organization is denied in flag/insight/import/audit paths; foreign/missing records are rejected before writes in KYC, imports, and reports.
- `OrganizationScopedRepositoryIntegrationTest` seeds Organizations A and B and runs against PostgreSQL 16 with the real Flyway migrations and Hibernate schema validation. It exercises scoped client, owner, import-batch, user, audit, flag, STR, CTR, and transaction aggregate queries; includes transaction-only flags, inconsistent client/transaction ownership, an A-owned batch uploaded by B, an A-owned batch without an uploader, an A-owned flag reviewed by B, and foreign-ID misses; verifies service/controller mutations do not change B's rows; reads the generated annual XLSX to assert it contains A's data but not B's or inconsistent records; and verifies shared `SystemConfig` JSON omits another Organization's updater metadata.
- `pnpm api:test` passes after the shared-configuration serialization regression fix, including the PostgreSQL integration test. The database is disposable Testcontainers state; no application/production database is touched.
- Springdoc was regenerated from the candidate API after the routes moved to `/api/v1`: all 40 operations across 35 resource paths are versioned, all local component references resolve, and the generated `SystemConfigResponse` schema has only `key`, `value`, and `updatedAt` (no `updatedBy`). The metadata schema is `ApiResponseMetadata`; direct user creation explicitly documents its `501` error envelope. `pnpm api:openapi` completed and updated the generated client types.
- Global threshold and system-configuration values remain shared, but both write routes now fail closed for all current Organization roles until a separately authenticated, audited platform authority is implemented. Direct user creation likewise remains disabled until the approved membership invitation flow can replace it. Task 0015 must still re-audit the whole product; this task is containment evidence, not a release security certification.
